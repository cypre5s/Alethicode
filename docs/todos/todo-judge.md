## 0. 总原则

### 0.1 硬性要求

- [ ] 不允许只做补丁式修补，必须消除结构性瓶颈。
- [ ] 不允许让业务后端继续直连执行节点作为长期方案。
- [ ] 不允许把 AI 放进判题热路径作为裁决依据。
- [ ] 不允许为了吞吐牺牲判题正确性。
- [ ] 不允许为了上线速度跳过影子对比与回归验证。
- [ ] 不允许保留两套长期并行的正式判题链路。
- [ ] 保留 `Judger` C 内核，不在本次升级中重写为 Rust / Go / C++。
- [ ] 判题控制面采用新增 `Go` 服务的方案。
- [ ] 安全优先级高于吞吐，吞吐优先级高于实现成本。

### 0.2 三条验收红线

- [ ] 判题结果一致性红线：新旧链路在同题目、同代码、同测试点、同资源限制下，结果必须一致；存在差异时，必须在切流前定位原因并关闭差异。
- [ ] 安全边界红线：业务后端不能直接访问执行节点；未注册节点、过期节点、伪造节点、重放请求全部必须被拒绝并记录审计。
- [ ] 队列可靠性红线：任何 submission 不允许无限期卡在 `QUEUED`、`LEASED`、`RUNNING` 状态；租约超时后必须被回收、重试或明确失败。

### 0.3 执行纪律

- [ ] 每一阶段都必须先完成本阶段验收，再进入下一阶段。
- [ ] 每一阶段都必须有明确产出物。
- [ ] 每一阶段都必须包含性能验收和安全验收。
- [ ] 任何接口变更都必须先冻结契约，再开发实现。
- [ ] 所有结论都必须基于固定环境、固定数据、固定版本、固定压测脚本复现。

## 1. 终态定义

### 1.1 目标架构

- [ ] Java 后端只负责 submission 创建、查询、重判入口，不再负责节点挑选和同步判题。
- [ ] 新增 `judge-control` 作为唯一判题控制面，负责队列、租约、节点管理、调度、结果汇总和审计。
- [ ] 执行节点只通过节点代理和 `judge-control` 通信，不对业务后端开放。
- [ ] `JudgeServer` 旧 Python 包装层不再承担正式长期职责，由新的轻量节点代理替代。
- [ ] `Judger` C 内核继续作为最终执行器，负责 `fork/exec`、`setrlimit`、`setuid/setgid`、seccomp。

### 1.2 目标任务状态机

- [ ] 统一状态机为：`QUEUED -> LEASED -> RUNNING -> FINISHED / FAILED / EXPIRED`
- [ ] 所有状态变化都有来源、时间戳、节点标识和审计记录。
- [ ] 所有状态都可从控制面单点查询。

### 1.3 目标安全模型

- [ ] 节点注册采用 bootstrap token。
- [ ] 注册成功后发放短期节点凭证。
- [ ] heartbeat、拉取任务、续租、结果上传全部使用短期凭证。
- [ ] 所有节点请求必须带时间戳、nonce、签名。
- [ ] 所有异常鉴权都必须有审计日志。

### 1.4 目标性能模型

- [ ] 调度依据不再是单一 `task_number`，而是 `available_slots`、`running_tasks`、`queue_depth`、窗口时延、失败率。
- [ ] 单个任务内部不再采用“每请求新建 `Pool(cpu_count())`”的模式。
- [ ] ACM 题默认首个非 AC 后短路停止；OI 题按题目规则执行全部测试点。
- [ ] debug、trace、正式判题统一走容量控制，不允许旁路。

## 5. 节点代理替换 JudgeServer

### 阶段目标

用新的轻量节点代理替换旧 Python `JudgeServer` 的重并发包装层，保留 `Judger` 为执行核心。

### 执行步骤

- [ ] 新节点代理只实现四类职责：注册、拉任务、执行、回报。
- [ ] 删除“每请求新建 `Pool(cpu_count())`”的模型。
- [ ] 节点并发固定由控制面下发的 `available_slots` 限制。
- [ ] ACM 题实现首个非 AC 后短路停止。
- [ ] OI 题保留完整测试点评分逻辑。
- [ ] debug / trace / 正式 submission 全部经过统一容量控制。
- [ ] 节点代理只读测试用例目录，不接入业务数据库。

### 产出物

- [ ] 新节点代理服务
- [ ] 节点执行配置模板
- [ ] 节点资源上报说明

### 验收标准

- [ ] 同一台机器上，新节点代理吞吐明显高于旧 `JudgeServer`。
- [ ] 节点并发数稳定受控，不出现 `workers * threads * Pool(cpu_count())` 的并发膨胀。
- [ ] debug、trace、正式 submission 不再互相抢占失控。
- [ ] 所有标准 submission 样本结果与旧链路一致。

## 7. Judger 安全加固

### 阶段目标

在保留 C 内核的前提下，补齐现代化资源治理和执行隔离。

### 执行步骤

- [ ] 保留现有 `setrlimit`、`setuid/setgid`、seccomp 机制。
- [ ] 在节点层补齐 cgroup v2：CPU、memory、pids、io 限制。
- [ ] 为节点容器启用只读根文件系统和最小 capability。
- [ ] 工作目录独立挂载，避免污染容器根目录。
- [ ] 明确区分编译用户、运行用户、SPJ 用户。
- [ ] SPJ 编译产物增加哈希校验和版本校验。
- [ ] 编译日志、运行日志、输出大小都增加严格上限。
- [ ] 节点代理上报自身镜像 digest、规则版本和安全 posture。

### 产出物

- [ ] 安全配置基线
- [ ] seccomp / cgroup / capability 配置说明
- [ ] SPJ 安全校验说明
- [ ] 安全审计事件表

### 验收标准

- [ ] fork 炸弹无法拖垮宿主机。
- [ ] 非法 syscall 会被拒绝并记录。
- [ ] 恶意大输出不能打满节点磁盘。
- [ ] 节点被攻破后无法直接横向访问业务后端。
- [ ] 所有安全策略可通过自动化测试复现验证。
