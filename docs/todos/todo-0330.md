# TODO 0330：面向计算机设计大赛 AI 赛道的作品强化方案

> 文档状态：比赛版方案  
> 更新时间：2026-03-30  
> 适用仓库：`/home/cypress/Alethicode`  
> 目标：在现有 OJ AI 主链路基础上，做出能征服比赛评委的旗舰 AI 能力，而不是继续堆叠零散功能

---

## 0. 这份文档的定位

这不是普通待办清单，也不是重新发明第二套 AI 产品。

这份文档只回答 4 个问题：

1. 在现有 Alethicode OJ AI 基础上，什么方向最值得做成比赛主秀
2. 哪些能力既有顶会/顶刊依据，又能在没有真实大规模学生数据时先做出效果
3. 如何在不破坏当前 `workflow` 主架构的前提下实现
4. 如何让现场 Demo、答辩材料、技术叙事三条线统一

本方案默认遵守当前项目的强约束：

- 不新增第二个学生 AI 入口
- 不把系统做成自由聊天机器人
- 不新建脱离题目页主工作流的旁路系统
- 不为了比赛炫技而引入无法解释、无法演示、无法评测的重模型方案
- 不改动现有 `Phase` 主枚举，只在既有主链路上增强

## 1. 一句话作品定位

### 推荐标题

`从 AC 到真懂：会识别认知偏差与空转状态的 AI 编程学习系统`

### 推荐电梯陈述

传统 OJ 只能判断代码对不对，普通大模型只能回答像不像。  
本系统进一步识别学生“哪里想错了”“什么时候已经空转”“下一步最该做什么”，
把在线判题升级成面向 Python 初学者的认知型学习系统。

### 对评委最重要的差异点

我们展示的不是“AI 会讲题”，而是：

1. AI 能先让学生暴露自己的思维预测
2. AI 能把学生预测和真实执行轨迹对齐，找出认知偏差
3. AI 能判断学生是有效坚持还是低效空转
4. AI 能给出最小、可执行、不过界的下一步干预

这会显著区别于：

- 普通 OJ + ChatGPT
- 普通错题本 + 总结文案
- 只有 AC / WA 反馈的做题系统

---

## 2. 为什么现在不该继续“补功能”，而该做“旗舰闭环”

从仓库现状看，项目已经具备相当完整的 AI 教学底座：

- 统一工作流：`READING / IDEATING / SCAFFOLDING / CODING / ERROR_FEEDBACK / AC_REVIEW / TRANSFER / CHAT`
- 统一证据层：`EvidencePack`
- 统一学习者画像：`LearnerState / mastery_by_kc / weak_kcs / memory_refs`
- 统一治理链路：`trace / eval / rollout`
- 已有能力：长期学习记忆、相似错误提醒、变量运行可视化、自适应渐退脚手架、多 Agent 协同

这意味着：

- 继续加一个“更会聊天”的 Agent，评委感知弱
- 继续加一个“更复杂的 KT 模型”，现场可见度弱
- 继续做零散页面增强，难形成作品记忆点

因此比赛版本不该再以“功能数”取胜，而应该以“单一闭环的完成度”取胜。

## 3. 顶会 / 顶刊依据

本方案只吸收能直接映射到当前工程结构的思想，不机械照搬论文模型。

### 3.1 DKT（NeurIPS 2015）

论文：`Deep Knowledge Tracing`

吸收点：

- 学生能力不是静态标签，而是交互序列
- 题目尝试顺序和对错历史对后续教学动作有价值

本项目映射：

- 继续保留现有 `mastery_by_kc` 主线
- 比赛版本不直接把 DKT 做成主秀，而是让它作为“为什么系统需要持续追踪学习过程”的理论支撑

### 3.2 AKT（KDD 2020）

论文：`Context-Aware Attentive Knowledge Tracing`

吸收点：

- 学习者状态应同时考虑题目难度、上下文和时间衰减
- 注意力权重有利于解释“为什么当前弱项是这个 KC”

本项目映射：

- 当前仍用可解释的轻量画像做在线决策
- 比赛材料中把 AKT 作为未来升级路线，而非当前强依赖

### 3.3 Data-Driven Hint Generation（IJAIED 2017）

论文：`Data-Driven Hint Generation in Vast Solution Spaces: a Self-Improving Python Programming Tutor`

吸收点：

- 对开放式编程任务，最有价值的不是给整题答案，而是给“下一步提示”
- 提示应该尽量贴近学生当前代码状态，而不是泛化说教

本项目映射：

- 在现有 `CODING / ERROR_FEEDBACK` 阶段增加“编辑级下一步提示”
- 让系统更像真正会推进学习过程的 Tutor

### 3.4 Continuous Hint Factory（JEDM）

论文：`The Continuous Hint Factory - Providing Hints in Vast and Sparsely Populated Edit Distance Spaces`

吸收点：

- 下一步提示可以基于相似历史轨迹和编辑距离近邻推断
- 提示目标不是“替学生完成”，而是“把学生往正确轨迹推一步”

本项目映射：

- 与现有相似错误检索、代码快照、长期记忆天然兼容
- 非真实大数据场景下，可先用规则 + 检索 + reference solution 形成首版

### 3.5 Wheel-Spinning Detection（EDM / JEDM 方向）

论文方向：`How quickly can wheel spinning be detected?` 等

吸收点：

- 学生持续失败不等于有效学习
- 系统需要识别“空转”并及时改变教学动作，而不是无限重复提示

本项目映射：

- 在 `ERROR_FEEDBACK` 和 `CODING` 阶段识别“非生产性坚持”
- 一旦命中，系统必须切换到救援动作，而不是继续给同类反馈

### 3.6 自我解释 / 认知外显（教育心理 + AI 教学系统）

虽然这里不完全是纯 CS 顶会，但它是比赛答辩中必须补上的理论环：

- 学生先预测，再看真实执行，有助于暴露错误心智模型
- 让学生说出“为什么这样想”比只看 AC 更能证明学会了

本项目映射：

- 认知偏差镜（Prediction vs Trace）将成为比赛现场最有冲击力的展示能力

## 4. 推荐主秀：只讲一个闭环

### 闭环名称

`预测 -> 对照 -> 识别偏差 -> 判定空转 -> 给出最小下一步干预`

### 为什么选它

因为它同时满足三件事：

1. **现场可见**：评委一眼就能看到学生“以为”和“实际”不一致
2. **技术可讲**：可自然串起 workflow、trace、LearnerState、memory、bandit、hint generation
3. **材料可写**：有明确输入、状态变化、输出、评测指标，不像纯体验优化那样空

### 不选什么

本轮不把以下方向作为主秀：

- 端到端重训练 Tutor 模型
- 独立多 Agent 自主协作系统
- 纯看板类数据可视化
- 只做一个更复杂的知识追踪模型替换

理由很简单：这些方向要么对评委不够“可见”，要么需要当前没有的真实数据规模。

## 5. 比赛版三大旗舰能力

## 5.1 旗舰一：AI 认知偏差镜（Cognitive Mismatch Mirror）

### 目标

让系统不仅知道“代码错了”，还知道“学生是怎么想错的”。

### 核心交互

在进入 `CODING` 或关键调试节点前，系统不直接讲答案，而是发出一个极短预测问题：

- 第一次循环结束后，`count` 会是多少？
- 当输入是 `3 5 1` 时，会先进入哪个分支？
- 列表遍历到第三个元素时，当前变量值是什么？

学生提交预测后，系统调用现有执行轨迹能力得到真实 trace，然后输出“认知偏差对照卡”：

- 学生预测值
- 真实执行值
- 第一个偏离步骤
- 偏差类型
- 下一步该检查的代码位置

### 为什么它有比赛杀伤力

- 视觉上强：预测和真实值的对照非常适合做高亮和动画
- 教学上强：直接证明系统理解的是“思维过程”，不是只认最终 AC
- 叙事上强：非常容易打动答辩评委

### 在现有架构中的最短落点

- 不新增新 Phase
- 在 `IDEATING / CODING / ERROR_FEEDBACK` 的卡片体系内新增：
  - `prediction_probe`
  - `cognitive_mismatch`
- 预测答案通过现有 `/api/ai/workflow/event` 继续上报，不新增独立入口

### fail-fast 规则

- 没有可安全执行的 Python trace，就不生成偏差镜卡片
- 预测问题无法绑定到具体变量/分支/循环步，不允许生成泛化问题
- 偏差定位不到代码片段，不展示“伪解释”

---

## 5.2 旗舰二：空转哨兵（Wheel-Spinning Sentinel）

### 目标

识别学生什么时候已经不是“努力”，而是“同类错误反复出现但没有学习增益”。

### 核心判断信号

首期只采用当前工程可直接获得的可解释信号：

- 连续失败提交次数
- 相同错误类别重复出现次数
- 同一代码片段附近高频修改但无通过增益
- 同一 KC 长时间低 mastery 且无改善
- 已经给过提示但学生仍重复原错误

### 命中后的动作

一旦命中空转，不继续输出普通错误解释，而是切换到救援动作：

1. 明确告知当前属于“重复卡住”
2. 指定唯一优先检查点
3. 根据当前 mastery 自动提升脚手架强度
4. 必要时触发“先预测再运行”的认知偏差镜

### 为什么它有比赛价值

- 它体现“系统会决定何时介入”，而不是永远被动回答
- 它能把已有相似错误、长期记忆、脚手架、画像全部串起来
- 它让系统从“会解释”升级成“会判断教学时机”

### 在现有架构中的最短落点

- 新增服务：`WheelSpinningSentinelService`
- 命中结果写入 `LearnerState.recommendedActionBias`
- 在 `TutorActionPolicy` 中作为更高优先级策略信号
- 新增卡片：
  - `rescue_plan`

### fail-fast 规则

- 证据不足时不允许贴“空转”标签
- 不做情绪化语言推断，只做行为级判定
- 不在首次失败时触发

---

## 5.3 旗舰三：编辑级下一步提示（Next-Step Edit Hint）

### 目标

把“你错了”升级成“你下一步最该改这里”。

### 核心输出

系统不输出整段标准答案，只输出最小可执行提示：

- 推荐先改哪一行或哪一段逻辑
- 这一改动的目标是什么
- 为什么先改这里而不是别处
- 预期会影响哪一种错误

### 推荐形式

```json
{
  "card_type": "next_step_hint",
  "focus_region": {
    "start_line": 6,
    "end_line": 8
  },
  "edit_goal": "先修正循环边界，而不是继续改输出格式",
  "why_now": "当前错误首次发生在第 3 次迭代，源头在遍历范围而不是 print 语句",
  "minimal_hint": "检查 range 的结束边界是否覆盖了最后一个元素",
  "expected_effect": "修复后可消除越界或漏统计问题"
}
```

### 为什么它有比赛价值

- 它比普通 hint 更像“懂代码状态”的 Tutor
- 它比直接给代码更安全，更符合教学边界
- 它能自然承接相似错误检索和认知偏差镜

### 在现有架构中的最短落点

- 不新增独立提示系统
- 在 `CODING / ERROR_FEEDBACK` 内新增 `next_step_hint`
- 优先基于：
  - 当前代码快照
  - reference solution 结构差异
  - 历史相似错误命中
  - 认知偏差镜定位结果

### fail-fast 规则

- 不输出完整修复代码
- 不给多个并列建议，强制只给一个最小优先动作
- 没有明确焦点区域时不输出编辑级提示

## 6. 可选加分项：AC 后微答辩（Micro Defense）

### 目标

解决“学生 AC 了，但不一定真懂”。

### 核心交互

在 `AC_REVIEW` 后，系统随机给一个极短追问：

- 如果输入为空列表，结果会怎样？
- 为什么这里要先初始化为 0？
- 如果把 `>` 改成 `>=`，会发生什么变化？

### 作用

- 非常适合答辩时讲“我们不鼓励答案主义”
- 和 `TRANSFER` 阶段天然衔接
- 可以作为后续长期记忆写入的新证据源

### 优先级判断

它很适合比赛材料，但不是主秀。

推荐顺序：

1. 先做认知偏差镜
2. 再做空转哨兵
3. 再做编辑级下一步提示
4. 最后补 AC 后微答辩

## 7. 与现有主架构的融合原则

### 7.1 不改主 Phase

现有：

`READING -> IDEATING -> SCAFFOLDING -> CODING -> ERROR_FEEDBACK -> AC_REVIEW -> TRANSFER`

本轮不新增 `PREDICTING` 之类的新阶段。  
原因：当前系统的最大价值就是主链路已经统一，比赛强化应该建立在这个稳定事实源上。

### 7.2 通过新 CardType 扩展，而不是新入口扩展

建议新增卡片：

- `prediction_probe`
- `cognitive_mismatch`
- `rescue_plan`
- `next_step_hint`
- `micro_defense`

### 7.3 通过现有 event_data 承载交互，不新增第二 API

继续使用：

- `POST /api/ai/workflow/event`

在 `event_data` 中扩展：

- `prediction_answer`
- `prediction_target`
- `rescue_ack`
- `micro_defense_answer`

### 7.4 通过现有 EvidencePack 组装证据

新增或增强的证据字段：

- `prediction`
  - 当前预测问题
  - 学生预测答案
  - 目标变量 / 目标步骤 / 目标分支
- `trace_alignment`
  - 真实 trace 命中步骤
  - 首次偏离位置
  - 偏差摘要
- `wheel_spinning`
  - 连续失败次数
  - 重复错误摘要
  - rescue 触发原因
- `edit_hint_context`
  - 焦点代码片段
  - 推荐改动目标

## 8. 推荐最小实现顺序

严格按比赛收益排序，不按技术炫技排序。

### 阶段 A：认知偏差镜 MVP

目标：

- 让评委第一次 Demo 就记住作品

任务：

- 新增 `prediction_probe` 与 `cognitive_mismatch` 卡片协议
- 在 Python trace 结果上增加“预测答案对齐”
- 前端做“预测 vs 真实”的对照卡片和高亮动画

验收：

- 能稳定演示 3 个初学者常见误区：
  - 循环次数误判
  - 条件分支误判
  - 累加变量变化误判

### 阶段 B：空转哨兵

目标：

- 让评委看到系统不只是解释，还会判断“何时应该介入”

任务：

- 新增 `WheelSpinningSentinelService`
- 规则判定连续失败和重复错误模式
- 命中后切换 `rescue_plan`

验收：

- 至少能稳定演示 2 条“普通 ERROR_FEEDBACK”和“空转救援”之间的差异路径

### 阶段 C：编辑级下一步提示

目标：

- 让系统看起来真正“会推进学生往前走”

任务：

- 新增 `next_step_hint` 卡片
- 绑定焦点代码区域
- 输出唯一优先动作

验收：

- 演示同一错误下，系统不会给整题答案，而是只给下一步编辑方向

### 阶段 D：AC 后微答辩

目标：

- 丰富材料层叙事，证明系统关心“真懂”而不是“刷 AC”

任务：

- 新增 `micro_defense` 卡片
- 和 `TRANSFER` 联动

验收：

- 至少准备 3 组题后追问模板用于比赛 Demo

## 11. 比赛现场 Demo 剧本

本项目必须按“1 条主线 + 2 次反转”来演示。

### Demo 角色

- 学生：Python 初学者
- 题目：含循环 + 条件判断 + 计数变量的基础题

### Demo 脚本

1. 学生进入题目页
2. 系统先发出一个超短预测问题
3. 学生答错
4. 系统展示真实 trace，并高亮“第一次偏离发生在这里”
5. 学生继续提交，重复犯同类错误
6. 系统触发空转哨兵，不再重复普通解释，而是切换为 rescue plan
7. 系统给出唯一下一步编辑提示
8. 学生修正后 AC
9. 系统追问一个微答辩问题，证明不是“蒙对”

### 评委最容易被打动的瞬间

- 预测值和真实值对照出现的那一刻
- 系统说出“你不是不会写，你是把第 3 次循环时的变量变化想错了”
- 系统不直接给答案，而是说“你先只改这一段”

## 12. 没有真实学生数据时，怎么做评测

当前现实约束是：未来可能拿到数据，但现在没有。

所以比赛版本必须采用“可验证、可复现、可答辩”的替代评测方式。

### 12.1 构建小型专家基准集

建立 20~30 条人工整理的初学者典型案例：

- 循环边界错误
- 计数器初始化错误
- 条件分支方向错误
- 输入处理错误
- 列表索引越界

每条样例包括：

- 题目
- 学生错误代码
- 学生常见错误预测
- 标准 trace
- 理想下一步提示
- 是否应判为空转

### 12.2 离线评测指标

- `mismatch_localization_accuracy`
  - 首次偏离步骤定位是否正确
- `rescue_trigger_precision`
  - 空转触发是否合理
- `next_step_actionability`
  - 下一步提示是否具体且可执行
- `answer_leak_rate`
  - 是否越界给整题答案
- `schema_pass_rate`
  - 卡片协议是否稳定

### 12.3 答辩表达方式

不要说“我们已经在真实课堂大规模验证”。  
要诚实地说：

- 当前已完成工程闭环与小样本专家基准验证
- 下一阶段将在真实课堂中收集交互数据，进一步验证学习收益

这样更稳，也更符合现在的真实状态。

## 13. 材料写作时的三大创新点

论文、路演、答辩 PPT 都应该收敛到以下 3 点，不要发散。

### 创新点 1：从结果反馈升级为认知偏差识别

传统 OJ 只判断结果，普通 AI 只解释结果。  
本系统通过“预测 - 执行轨迹 - 对照”识别学生错误心智模型。

### 创新点 2：从被动答疑升级为空转状态干预

系统不是无限重复提示，而是判断何时学生已进入低效空转，并主动切换教学动作。

### 创新点 3：从泛化建议升级为编辑级下一步提示

系统不直接给标准答案，而是给最小、可执行、可验证的下一步编辑方向。

## 14. 非目标

为了保证比赛版本收敛，本轮明确不做：

- 不做端到端大模型微调
- 不做真正在线学习的 bandit 自动放量
- 不做跨课程大规模知识迁移上线
- 不做第二套独立大屏 / 第二个学生入口
- 不做“看起来很智能但无法解释”的黑箱推荐

---

## 15. 结论

如果比赛目标是“炫技且征服评委”，那么最优路线不是继续堆 AI 功能，而是把现有底座收束成一个极强的主秀闭环：

`认知偏差镜 + 空转哨兵 + 编辑级下一步提示`

这条路线的优势是：

- 对评委可见
- 对材料可讲
- 对现有工程可接
- 对未来真实课堂数据可扩展

它既不是普通 OJ，也不是普通大模型套壳，而是一个开始具备“诊断学习过程”能力的 AI 编程学习系统。
