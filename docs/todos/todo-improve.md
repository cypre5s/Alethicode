## 0. 文档定位

本文档用于定义下一阶段 OJ AI 的 5 项核心增强能力：

1. 相似错误提醒，融合进入 `ERROR_FEEDBACK` Agent
2. AI 变量运行可视化
3. 多 Agent 协同升级
4. 长期学习记忆
5. 受控生成

本文档不是灵感清单，而是标准需求文档。输出目标是：

- 明确为什么做
- 明确做成什么
- 明确和现有系统如何融合
- 明确哪些属于首期必做，哪些不做
- 明确验收标准

## 1. 背景与问题

当前项目已经具备以下基础能力：

- 统一 AI 工作流：`READING / IDEATING / SCAFFOLDING / CODING / ERROR_FEEDBACK / AC_REVIEW / TRANSFER / CHAT`
- 统一 AI 面板与卡片协议
- 知识图谱、KC 关联、易错点管理
- 个性化错题本 `ai_learner_notebook`
- 学习事件、代码快照、工作流轨迹、检索日志
- 基于证据包 `EvidencePack` 的工作流生成链路

当前真正的问题不是“没有 AI”，而是“AI 还不够像一个真正理解学生的学习系统”。

对 Python 初学者、尤其是非科班学生，当前仍有 5 个明显短板：

1. 出错后知道“错了”，但不知道“这次和自己过去的错误有什么关系”
2. 看不清代码运行过程，尤其看不懂变量如何变化
3. 不同 Agent 之间仍偏串行，缺乏共享学生状态的协作机制
4. 历史学习信息已记录，但还没有形成稳定、可调用、可衰减的长期记忆
5. LLM 已参与多节点生成，但受控程度还不够强，仍存在输出漂移、内容越界和质量不稳定风险

---

## 2. 建设目标

## 2.1 一句话目标

把当前 OJ AI 从“单次任务响应系统”升级为“面向 Python 初学者的长期学习教练系统”。

## 2.2 核心目标

- 让 AI 能识别学生“又犯了和以前相似的错误”
- 让 AI 能把程序运行过程讲清楚，而不是只解释结果
- 让多个 Agent 共享同一份学生状态和证据，而不是各自孤立工作
- 让系统积累并使用长期学习记忆，而不是只有短期会话上下文
- 让所有生成结果都落在受控边界内，稳定、可验证、可灰度

## 2.3 非目标

本期不做以下事情：

- 不新增独立的第二个 AI 学生入口
- 不做无边界的自由聊天机器人
- 不直接训练大模型或重做模型底座
- 不为了“更像 Agent”而牺牲现有工作流稳定性
- 不引入和现有表结构、工作流、知识图谱完全割裂的新系统

## 3. 目标用户与典型场景

## 3.1 目标用户

- 刚开始学习 Python 的学生
- 非计算机专业、缺少算法和编程基础的学生
- 能看懂题意，但容易在输入输出、变量、循环、边界、类型转换上出错的学生

## 3.2 典型场景

### 场景 A：重复犯错但自己没有意识到

学生当前提交出现 `IndexError` 或边界错误。系统不只告诉他“越界了”，还指出这和他之前某道题的错误模式高度相似，并引导他优先检查哪一段逻辑。

### 场景 B：不会调试，不知道程序怎么跑

学生写了循环和条件判断，但不知道程序执行到了哪一步。系统用变量变化过程、循环迭代过程和关键分支解释，帮助他看懂程序在做什么。

### 场景 C：同一学生在不同题上反复卡在同类问题

系统识别该学生长期在“输入处理”“类型转换”“边界条件”上反复出错，在新题中提前做风险提示，并调整 Agent 的提示策略。

### 场景 D：多个 Agent 给出的指导不一致

学生先看了思路分析，再进入编码，再进入错误诊断。如果每个 Agent 不共享状态，就容易出现前后不一致。系统需要让多个 Agent 使用统一的学生状态、统一的证据和统一的安全边界。

## 4. 总体产品原则

### 4.1 唯一学生主入口

所有增强能力都必须融入现有统一 AI 工作流和统一面板，不新增第二个聊天框或第二条学习链路。

### 4.2 面向初学者

所有输出必须优先满足“学生能看懂”。不使用默认偏专家化表达，不以术语堆砌代替教学解释。

### 4.3 先证据，后生成

所有关键生成节点必须优先使用结构化证据，不允许直接把会话历史无约束拼接给模型。

### 4.4 先受控，后增强

新增 AI 能力必须先满足结构化输出、边界控制、回放记录和灰度能力，之后再追求更强效果。

### 4.5 先融合，后扩张

优先复用已有的：

- `ai_learner_notebook`
- `ai_learning_event`
- `ai_code_snapshot`
- `ai_workflow_session / event / checkpoint`
- `ai_problem_kc_mapping`
- `EvidencePack`
- `ai_retrieval_log`

---

## 4.6 实施纪律

本次 5 个能力的落地，必须严格遵守以下执行纪律：

`迁移 → 自检 → 单元测试 → 集成测试 → 通过确认 → 迁移下一模块`

约束如下：

- 任意一步不通过，必须原地修复，不得跳过
- 未完成“通过确认”，不得并行推进下一个能力模块
- 每个模块都必须有独立的输入、处理流程、状态变化、输出和上下游影响检查
- 每个模块都必须输出“完成后的期望验收结果”，作为通过确认的唯一标准
- 所有实现必须沿现有主链路演进，不允许通过旁路功能先上线再回补主链

## 4.7 模块迁移顺序

本次需求按以下顺序推进，不允许跳序：

1. 受控生成
2. 长期学习记忆
3. 相似错误提醒
4. 多 Agent 协同升级
5. AI 变量运行可视化

排序理由：

- `受控生成` 是所有新能力的安全和协议底座
- `长期学习记忆` 是相似错误提醒和多 Agent 个性化协作的共同数据底座
- `相似错误提醒` 先落到 `ERROR_FEEDBACK`，能最快形成用户可感知价值
- `多 Agent 协同升级` 依赖前两层数据和生成边界已经稳定
- `变量运行可视化` 技术复杂度最高，适合在编排和受控框架稳定后推进

## 4.8 单模块通过确认模板

每个模块在进入“通过确认”时，必须同时提交以下结果：

1. 自检结果
   说明输入、处理流程、状态变化、输出、上下游影响均已链路检查通过
2. 单元测试结果
   覆盖该模块新增规则、协议和失败分支
3. 集成测试结果
   覆盖真实工作流链路、数据写入和前后端契约
4. 期望验收结果
   用学生视角和系统视角明确说明“做完后应该看到什么”
5. 风险结论
   说明本模块已知边界，不得将未验证推测表述为已完成事实

## 5. 总体方案概述

本期统一方案为：

`证据层增强 + 记忆层增强 + Agent 编排层增强 + 受控生成层增强`

### 5.1 四层结构

#### 第一层：证据层

新增与复用的证据包括：

- 当前题目上下文
- 当前代码快照
- 当前提交结果与错误信息
- 错题本相似错误片段
- 历史学习记忆
- 知识图谱弱点与 KC 信息

#### 第二层：记忆层

把错题本、学习事件、复盘摘要等内容沉淀为可检索、可衰减、可引用的长期学习记忆。

#### 第三层：编排层

多 Agent 不再只靠前端阶段切换，而是由统一编排层根据学生状态、证据和当前 phase 决定：

- 哪个 Agent 当前为主
- 哪些 Agent 提供辅助信号
- 输出是否允许继续推进

#### 第四层：生成层

所有生成任务进入统一受控生成框架，执行：

- 输入结构化
- 输出 schema 校验
- 风险扫描
- 越界拦截
- 回退与失败显式暴露

## 6. 需求一：相似错误提醒，融合进入 `ERROR_FEEDBACK` Agent

## 6.1 目标

在学生出错时，不只解释当前错误，还要结合该学生历史错误，提示“这次和你以前哪类错误相似”，帮助学生形成错误模式意识。

## 6.2 用户价值

对初学者来说，最常见的问题不是不会改一次错误，而是不知道自己在反复犯同类错误。相似错误提醒的价值是让学生看到“错误模式”，而不是只看到“单次错误”。

## 6.3 功能定义

当工作流进入 `ERROR_FEEDBACK` 时，系统自动从该学生的错题本和长期记忆中检索历史相似错误，生成结构化提示。

输出内容至少包括：

- 相似度最高的历史错误摘要
- 本次错误与历史错误的相同点
- 本次错误与历史错误的不同点
- 建议优先检查的代码位置或逻辑点

## 6.4 融合方式

本功能必须融合进入现有 `ERROR_FEEDBACK` Agent，不允许新增独立“相似错误按钮”或旁路功能。

`ERROR_FEEDBACK` 的输入证据新增：

- `similar_notebook_hits`
- `similar_memory_hits`

`error_diagnosis` 卡片协议新增字段：

- `similar_error_summary`
- `similar_error_refs`
- `repeat_pattern_detected`

## 6.5 处理流程

1. 学生提交出错
2. 系统进入 `ERROR_FEEDBACK`
3. 从当前错误信息、代码摘要、题目 KC 生成检索 query
4. 在当前学生私有错题本和长期记忆中检索相似记录
5. 对候选结果 rerank
6. 将 top-k 结果写入 `EvidencePack`
7. `ERROR_FEEDBACK` Agent 基于当前错误和历史相似错误生成诊断卡片

## 6.6 AI 技术要求

- 必须采用混合检索：元数据过滤 + 语义检索 + rerank
- 检索范围必须限定在当前学生私有数据，不得跨学生召回
- 不允许仅做关键词匹配
- 相似错误输出不得直接给标准答案，只能给定位与纠错方向

## 6.7 验收标准

- 学生出现重复类型错误时，系统可稳定检索到至少 1 条历史相似记录
- 错误诊断卡片中可显示相似错误摘要和引用来源
- 无历史记录时系统正常退化为标准错误诊断，不报错、不空白
- 不得出现引用其他学生数据的情况

## 6.8 通过确认后的期望验收结果

本模块完成后，预期系统应表现为：

- 学生再次犯同类错误时，不再只看到“答案错误/运行时错误”，而是会明确看到“这和你之前哪类错误相似”
- `ERROR_FEEDBACK` 卡片会出现“历史相似错误”区域，并给出本次优先检查点
- 教师或开发者可在 trace / retrieval log 中看到该次错误诊断确实消费了相似错误证据
- 当学生没有历史记录时，系统仍保持现有错误诊断能力，不出现额外空白区或异常状态

## 7. 需求二：AI 变量运行可视化

## 7.1 目标

帮助学生看懂程序是怎么一步步运行的，尤其看懂：

- 变量值如何变化
- 循环执行了几次
- 分支条件为什么成立或不成立
- 当前程序输出为什么与预期不同

## 7.2 用户价值

对 Python 初学者，很多问题不是“不会写语法”，而是“不会 mentally execute 程序”。变量运行可视化的核心价值，是把程序的动态行为讲清楚。

## 7.3 功能定义

系统在以下场景提供变量运行可视化：

- 学生主动点击“看程序怎么跑”
- `ERROR_FEEDBACK` 发现问题适合通过运行过程解释
- `CODING` Agent 判断学生卡在局部执行理解上

系统输出一个结构化运行过程视图，至少包含：

- 输入样例
- 每一步关键代码位置
- 当前关键变量快照
- 当前输出
- AI 教学解释

## 7.4 融合方式

本功能作为统一 AI 卡片的一种新能力，不新增独立系统。

建议新增卡片类型：

- `execution_trace_explainer`

可由 `CODING` 或 `ERROR_FEEDBACK` 触发。

## 7.5 处理流程

1. 获取当前代码和示例输入
2. 进入受控执行或静态推演流程
3. 抽取关键执行步
4. 生成变量变化轨迹
5. 由 LLM 将轨迹翻译成适合初学者的中文说明
6. 输出结构化可视化卡片

## 7.6 AI 技术要求

- 必须优先使用程序执行轨迹或 AST/CFG 分析，不允许纯靠 LLM 幻觉推演
- LLM 只负责教学解释，不负责伪造运行结果
- 对无法安全执行的代码必须 fail-fast，明确返回“当前无法生成运行轨迹”
- 首期优先支持 Python3

## 7.7 验收标准

- 对简单顺序、分支、循环程序可稳定生成变量变化过程
- 解释文本必须和结构化轨迹一致
- 轨迹无法生成时，前端可显示清晰失败原因
- 学生能从卡片中看出“哪一步开始偏离预期”

## 7.8 通过确认后的期望验收结果

本模块完成后，预期系统应表现为：

- 学生在 `CODING` 或 `ERROR_FEEDBACK` 阶段可以看到“程序是怎么一步步跑的”，而不是只看到静态文字解释
- 对 Python 初学者常见的小程序，系统能展示关键变量如何变化、循环跑了几轮、在哪一步开始和预期不一致
- 教学解释与运行轨迹一一对应，学生能通过卡片直接定位“哪一步理解错了”
- 对无法安全执行或无法稳定推演的代码，系统会明确说明“当前无法生成运行轨迹”，而不是输出伪造过程

## 8. 需求三：多 Agent 协同升级

## 8.1 目标

让多个 Agent 基于同一份学生状态和证据协同工作，而不是各自只看到局部上下文。

## 8.2 用户价值

学生最怕 AI 前后矛盾。前一个 Agent 说“你的思路基本对”，后一个 Agent 又像没看过一样重新讲一遍。多 Agent 协同的价值，是让系统表现得像一个连续的老师，而不是多个断裂的机器人。

## 8.3 功能定义

建立统一的 Agent 编排协议，使 `READING / IDEATING / CODING / ERROR_FEEDBACK / AC_REVIEW / TRANSFER / CHAT` 都共享：

- 当前 phase
- 当前题目上下文
- 当前代码与提交状态
- 知识图谱弱点
- 相似错误检索结果
- 长期学习记忆
- 最近关键 checkpoint

## 8.4 融合方式

不做“多个 Agent 同时对话”的 UI，不新增多面板。  
本期只做服务端多 Agent 协同和策略编排升级。

表现形式仍然是统一 AI 面板，但每次输出由：

- 主 Agent
- 辅助 Agent 信号
- 编排层决策

共同产生。

## 8.5 处理流程

1. 编排层接收当前事件和上下文
2. 判断主责任 Agent
3. 选择可参与的辅助 Agent 信号
4. 聚合共享证据
5. 生成统一输出
6. 写入 trace，记录“谁主导、谁辅助、采用了哪些信号”

## 8.6 AI 技术要求

- 编排必须由服务端完成，不允许只在前端拼装逻辑
- 必须保留主 Agent 概念，不做完全去中心化自由辩论式 Agent
- 辅助 Agent 输出必须结构化，不允许多段自由文本互相污染
- 所有协同决策必须可回放、可记录、可评测

## 8.7 验收标准

- 同一题内多阶段输出不再出现明显上下文断裂
- trace 中可明确记录主 Agent 和辅助 Agent 参与信息
- `ERROR_FEEDBACK` 可消费 `IDEATING/CODING` 阶段沉淀的信息
- `CHAT` 可读当前工作流状态，而不是脱离主链路

## 8.8 通过确认后的期望验收结果

本模块完成后，预期系统应表现为：

- 学生在同一道题里连续使用多个 Agent 时，会明显感受到系统“记得自己刚才做过什么”
- `IDEATING`、`CODING`、`ERROR_FEEDBACK`、`CHAT` 的回答风格和上下文保持连续，不再像不同机器人各说各话
- 系统内部可明确回放：这次输出是谁主导、用了哪些辅助信号、依赖了哪些共享证据
- 前端仍保持单一 AI 面板，不增加新的学习入口或多窗口协作形态

## 9. 需求四：长期学习记忆

## 9.1 目标

把学生的历史错题、学习事件、复盘、反思等内容沉淀为可调用、可衰减、可更新的长期学习记忆。

## 9.2 用户价值

一个真正好的 AI 教练，不应该每次都像第一次见到学生。系统要能逐步知道：

- 这个学生总在哪类问题上卡住
- 这个学生更适合什么样的解释方式
- 这个学生最近正在补什么知识点

## 9.3 功能定义

长期学习记忆由三部分组成：

1. 错误记忆
   来源：错题本、错误诊断、相似错误检索
2. 学习偏好记忆
   来源：交互反馈、AI helpful/unhelpful、历史选择
3. 掌握状态记忆
   来源：知识图谱、提交结果、复盘与迁移表现

## 9.4 融合方式

长期记忆不直接暴露为独立页面功能，而是作为系统内部能力服务于：

- `IDEATING`
- `CODING`
- `ERROR_FEEDBACK`
- `AC_REVIEW`
- `CHAT`
- 推荐与复习任务生成

错题本是长期学习记忆的首个主来源，但不是唯一来源。

## 9.5 处理流程

1. 学生产生新的错误、反思、复盘或反馈
2. 系统抽取可长期保存的记忆单元
3. 为记忆打上类型、置信度、时间、来源、失效策略
4. 写入长期学习记忆存储
5. 后续按当前任务场景召回

## 9.6 AI 技术要求

- 必须区分短期会话上下文与长期学习记忆
- 长期记忆必须具备：
  - `memory_type`
  - `confidence`
  - `source`
  - `updated_at`
  - `expires_at` 或衰减规则
- 不能把全部历史聊天原文无差别堆进 prompt
- 记忆写入必须是“抽取后的结构化记忆”，不是原始对话存档

## 9.7 验收标准

- 系统可稳定调用长期记忆生成个性化提示
- 陈旧或低置信记忆不会长期污染当前决策
- 新的学生反思和复盘可转化为记忆单元
- 记忆缺失时系统仍可正常运行

## 9.8 通过确认后的期望验收结果

本模块完成后，预期系统应表现为：

- 同一个学生在不同题目、不同时间再次进入系统时，AI 能体现出“认识这个学生”的连续性
- 学生过去的错题、反思、偏好和复盘结果，会转化为后续可用的个性化提示，而不是停留在孤立记录
- 陈旧记忆不会长期霸占提示内容，系统能随着学生进步逐步更新判断
- 开发和评测侧可以清楚看到：哪些输出来自长期记忆，哪些来自当前题证据

## 10. 需求五：受控生成

## 10.1 目标

建立统一的受控生成框架，确保所有 LLM 输出都满足：

- 不直接泄题
- 结构稳定
- 内容可校验
- 风险可拦截
- 失败可显式暴露

## 10.2 用户价值

对教育产品，生成能力不是越自由越好，而是越可控越好。学生需要的是“可靠的教学输出”，不是“偶尔很聪明但经常越界的回答”。

## 10.3 功能定义

所有关键节点统一进入受控生成框架，至少覆盖：

- 思路分析
- 骨架代码
- 错误诊断
- AC 复盘
- 迁移练习
- 变量运行可视化说明
- Chat 模式的教学回答

## 10.4 关键能力

### 10.4.1 输入受控

模型输入必须来自结构化证据，不允许直接拼接大量非必要上下文。

### 10.4.2 输出 schema 校验

每一类卡片输出必须有明确 schema，缺字段即失败。

### 10.4.3 风险拦截

必须识别并拦截：

- 直接答案
- 完整可提交代码
- 脱离学生当前阶段的过度解释
- 与结构化证据不一致的幻觉内容

### 10.4.4 多轮重试受控

允许有限重试，但必须显式带着“缺了什么字段”“违反了什么规则”重试，不允许无信息重复请求。

### 10.4.5 生成日志

所有关键生成必须写入可审计日志，支持回放和评测。

## 10.5 融合方式

受控生成不是单独功能，而是本次全部需求的共同底座。

## 10.6 AI 技术要求

- 统一使用 schema 验证
- 统一使用内容风险扫描
- 统一记录 generation log
- 统一支持 fail-fast
- 对高风险场景必须优先输出引导式提示而不是结果

## 10.7 验收标准

- 各类卡片输出协议稳定，无关键字段缺失
- 出现越界生成时可被拦截
- 生成失败可向前端返回明确失败原因
- trace 和 generation log 可追踪一次完整生成过程

## 10.8 通过确认后的期望验收结果

本模块完成后，预期系统应表现为：

- 各类 Agent 和卡片即使继续增强，也不会频繁出现字段缺失、协议漂移和输出风格失控
- 学生无法轻易从系统拿到完整标准答案或可直接提交代码，教学边界清晰可控
- 一旦生成失败，前端、后端、测试三侧都能看到明确失败原因，而不是“看起来成功但内容异常”
- 后续新增任何 AI 卡片或工作流节点，都能复用统一受控生成底座，而不是各自私接 LLM

## 16. 后端实施拆分

本章用于把总需求拆成后端可直接执行的模块清单。  
执行时仍必须遵守：

`迁移 → 自检 → 单元测试 → 集成测试 → 通过确认 → 迁移下一模块`

## 16.1 模块一：受控生成后端收口

### 16.1.1 改动范围

- 工作流统一生成入口
- 卡片 schema 注册与校验
- 风险拦截规则
- generation log 持久化
- fail-fast 返回结构

### 16.1.2 后端任务

- 统一梳理所有会调用 LLM 的节点，禁止绕开统一生成链路
- 为变量运行可视化说明预留受控生成入口
- 对 `READING / IDEATING / CODING / ERROR_FEEDBACK / AC_REVIEW / TRANSFER / CHAT` 的输出协议做统一校验
- 补齐高风险文本扫描与拦截
- 补齐生成失败日志和错误原因返回

### 16.1.3 自检要点

- 所有生成节点是否都走统一入口
- 所有卡片是否都有 schema
- schema 缺字段时是否 fail-fast
- 风险输出是否会被拦截而不是透传
- generation log 是否完整记录

### 16.1.4 后端通过确认结果

- 任一工作流节点输出不再出现“部分字段缺失但仍标记成功”
- 高风险生成结果在服务端即被拦截
- generation log 可完整回放一次生成链路

## 16.2 模块二：长期学习记忆后端落地

### 16.2.1 改动范围

- 错题本到记忆单元的抽取
- 学习事件到记忆单元的抽取
- 记忆表结构或现有记忆能力扩展
- 记忆召回服务
- 记忆衰减与过期规则

### 16.2.2 后端任务

- 定义长期学习记忆的结构化字段
- 从 `ai_learner_notebook`、学习反馈、复盘结果中抽取记忆单元
- 建立记忆召回接口或服务层能力
- 明确短期上下文与长期记忆的使用边界
- 加入更新时间、置信度、来源和过期策略

### 16.2.3 自检要点

- 错题本是否能稳定生成记忆单元
- 同一来源重复写入是否会污染记忆
- 过期或低置信记忆是否可正确降权
- 当前题证据和长期记忆是否没有混淆

### 16.2.4 后端通过确认结果

- 学生历史反思、错题和复盘能被召回为结构化记忆
- 记忆数据不会无限堆积成不可控 prompt 原文
- 记忆召回结果可用于后续工作流节点

## 16.3 模块三：相似错误提醒后端接入

### 16.3.1 改动范围

- 私有错题本检索
- 相似错误 query 生成
- 混合检索与 rerank
- `ERROR_FEEDBACK` 证据包增强
- `error_diagnosis` 输出增强

### 16.3.2 后端任务

- 将当前错误、代码摘要、KC、submission 信息转成检索 query
- 只在当前学生私有错题本与记忆范围内召回
- 对召回结果做排序与裁剪
- 将结果写入 `EvidencePack`
- 输出结构化相似错误字段给 `ERROR_FEEDBACK`

### 16.3.3 自检要点

- 检索是否严格按 `user_id` 隔离
- 无历史记录时是否回退正常
- 相似错误内容是否只给定位与改错方向
- retrieval log 是否能区分新引入的记忆来源

### 16.3.4 后端通过确认结果

- 相似错误召回可稳定用于 `ERROR_FEEDBACK`
- 服务端可证明该次诊断真实使用了历史错误证据
- 不存在跨学生泄露数据风险

## 16.4 模块四：多 Agent 协同后端编排

### 16.4.1 改动范围

- Agent 编排策略
- 主 Agent / 辅助 Agent 协议
- 共享证据汇聚
- 协同 trace 与决策日志

### 16.4.2 后端任务

- 建立主 Agent 与辅助 Agent 的结构化协作协议
- 在服务端聚合共享证据，不允许前端拼装
- 输出中记录谁主导、谁提供了辅助信号
- 让 `CHAT` 也能消费当前工作流状态

### 16.4.3 自检要点

- 协同是否完全发生在服务端
- 协同决策是否可回放
- 辅助 Agent 是否只输出结构化信号
- 主 Agent 是否保持唯一责任归属

### 16.4.4 后端通过确认结果

- 同题跨阶段输出连续，且日志可清晰回放协同决策
- `ERROR_FEEDBACK` 和 `CHAT` 能消费上游阶段沉淀的有效状态

## 16.5 模块五：变量运行可视化后端链路

### 16.5.1 改动范围

- Python 代码执行轨迹抽取
- 关键步裁剪
- 变量快照结构
- 说明卡片受控生成

### 16.5.2 后端任务

- 设计可控的 Python 执行轨迹抽取方式
- 将关键执行步转成结构化快照
- 只把轨迹解释交给 LLM，不把运行事实交给 LLM 自行脑补
- 将输出接入统一卡片协议

### 16.5.3 自检要点

- 轨迹是否可重复生成
- 轨迹与解释是否一致
- 失败态是否显式暴露
- 是否只支持首期明确范围内的 Python 场景

### 16.5.4 后端通过确认结果

- 对简单 Python 代码，系统可稳定输出可解释运行轨迹
- 解释内容与真实轨迹一致，不依赖模型幻觉

## 18. 测试与验收拆分

本章用于把测试要求从总文档中拆成独立执行清单。  
所有测试仍必须绑定模块门禁，不允许只跑全量回归而跳过单模块确认。

## 18.1 单元测试拆分

### 18.1.1 受控生成

- schema 校验通过/失败
- 风险文本拦截
- 受控重试规则
- fail-fast 返回结构

### 18.1.2 长期学习记忆

- 记忆抽取
- 记忆更新
- 记忆过期/降权
- 空记忆与低置信记忆分支

### 18.1.3 相似错误提醒

- query 生成
- 私有范围过滤
- rerank 规则
- 无历史记录分支

### 18.1.4 多 Agent 协同

- 主 Agent 选择
- 辅助 Agent 信号聚合
- 共享证据消费
- 协同决策日志结构

### 18.1.5 变量运行可视化

- 关键执行步抽取
- 变量快照结构
- 失败态结构
- 解释文本与轨迹绑定关系

## 18.2 集成测试拆分

### 18.2.1 受控生成

- 真实工作流节点生成与日志落库
- 高风险回答被拦截

### 18.2.2 长期学习记忆

- 错题本/反思/复盘进入记忆层
- 后续工作流节点可召回记忆

### 18.2.3 相似错误提醒

- 学生重复犯错后，`ERROR_FEEDBACK` 命中历史相似错误
- 响应体、trace、retrieval log 三处一致

### 18.2.4 多 Agent 协同

- 同一 session 跨阶段上下文连续
- 主 Agent / 辅助 Agent 决策可回放

### 18.2.5 变量运行可视化

- `CODING` 和 `ERROR_FEEDBACK` 真实链路中可触发轨迹卡片
- 前端卡片协议与后端结构一致

每个模块进入“通过确认”前，必须逐项打勾：
