# Alethicode 实训总结报告

> 报告版本：v1.0  
> 项目名称：Alethicode 智能在线评测平台  
> 说明：当前未发现用户提到的附件模板，本文按通用高校实训总结报告结构编写，可迁移到学院模板。

## 1. 实训任务

本次实训的任务是完成一个具备实际业务价值和工程复杂度的软件项目，并提交完整项目代码、技术文档、实训总结报告、答辩 PPT 和功能演示视频。项目选题为 Alethicode：面向非计算机专业 Python 初学者的 AI 智能在线评测平台。

项目需要解决传统 OJ 对初学者反馈不足、AI 工具脱离课堂上下文、教师难以低成本进行个性化教学支持等问题。最终系统需要同时具备学生练习、自动判题、AI 辅导、课件问答、课堂管理、后台维护和工程部署能力。

## 2. 实训目标

1. 掌握前后端分离 Web 应用的完整开发流程。
2. 掌握 Spring Boot、Vue、数据库、缓存、微服务和部署编排的综合使用。
3. 理解在线评测系统的题库、提交、判题和结果展示流程。
4. 理解 AI Tutor、RAG、Prompt、学习者画像和可观测性在教育场景中的应用。
5. 能够编写符合规范的项目计划、需求规格、概要设计、详细设计、测试报告和总结文档。
6. 能够通过 PPT 和功能演示视频清晰展示项目价值、技术架构和实现成果。

## 3. 实训过程

### 3.1 需求分析阶段

在需求分析阶段，首先明确系统面向的核心用户是 Python 初学者、教师和管理员。学生需要做题、提交、查看反馈和获得 AI 辅导；教师需要管理班级、作业和学情；管理员需要维护题库、用户、判题服务器、AI 配置和系统运行状态。

需求分析的重点不是简单列出页面，而是围绕学习闭环梳理功能：学生提交代码产生真实学习信号，系统根据判题结果和历史记录构建学习上下文，AI Tutor 再基于上下文给出阶段化帮助，最后通过复盘、错题和推荐形成持续学习。

### 3.2 概要设计阶段

概要设计阶段确定了“Vue 前端 + Spring Boot 主后端 + Python AI 微服务 + PostgreSQL/Redis 等基础设施”的总体架构。Java 后端承担主要业务入口，前端负责学习和管理交互，`tutor-graph` 承担复杂 AI Tutor 工作流，`alethicode-rag` 承担课件检索增强。

这一阶段最重要的收获是理解系统边界：在线评测、AI 工作流、RAG 检索、课堂协作和运维观测看似复杂，但只要明确每个模块的职责和数据流，就能降低整体复杂度。

### 3.3 详细设计阶段

详细设计阶段进一步拆解账号、题库、提交、AI Tutor、语言包、课堂、管理端、安全和可观测性。后端按 Controller、Service、DTO、Repository/JdbcTemplate 和 Config 分层，前端按学生端、管理端、页面、组件和 API 分层。

AI Tutor 是详细设计中最复杂的部分。为了避免 AI 只进行泛泛回答，系统引入 EvidencePack 收集题目、提交、课件和学习者画像，再通过 Reflection 对回答进行自检。这样设计后，AI 能更贴近真实学习过程，也更适合课堂教学要求。

### 3.4 编码实现阶段

编码实现阶段涉及 Java、JavaScript/Vue、Python、SQL 和 Docker 配置等多种技术。项目中后端使用 Spring Boot 3.5.12 和 Java 21，前端使用 Vue 3.5 和 Vite 7.1，微服务使用 FastAPI、LangGraph 和 LightRAG，数据库使用 PostgreSQL 和 Flyway。

在实现过程中，最重要的是保持模块边界和数据一致性。数据库变更通过 Flyway 管理，服务之间通过明确接口调用，前端通过 API 契约和路由组织页面。对于外部 LLM、Embedding、Judge Server 等依赖，系统通过配置、健康检查、缓存和异常处理降低风险。

### 3.5 测试与调试阶段

测试阶段覆盖后端单元测试、控制器契约测试、集成测试、前端单元/契约测试、E2E 测试和微服务 pytest。项目测试目录中已经包含较多测试资产，说明系统不是只追求功能堆叠，也关注回归验证和工程质量。

调试过程中，外部服务配置、数据库迁移、前端路由权限和 AI 调用链路是最容易出问题的地方。通过日志、Actuator、Prometheus、Jaeger 和 Sentry/GlitchTip 等工具，可以更快定位问题。

### 3.6 文档与交付阶段

文档阶段按课程要求补充项目计划、需求规格说明书、概要设计说明书、详细设计说明书、测试计划和报告、项目总结、实训总结、PPT 内容稿和演示视频脚本。为了避免文档与代码不一致，本文档包优先参考构建配置、路由、控制器、迁移和测试目录。

## 5. 遇到的问题与解决方法

| 问题 | 分析 | 解决方法 |
|---|---|---|
| 系统模块多，容易范围失控 | OJ、AI、RAG、课堂和管理端都很复杂 | 按学习闭环划分主流程，答辩聚焦核心路径。 |
| 文档可能与代码不一致 | 项目迭代较快，旧文档容易过期 | 以代码、配置、路由和迁移为事实基线重新编写。 |
| AI 输出不稳定 | 受模型、上下文和 Prompt 影响 | 使用 EvidencePack、Reflection、引用和拒答边界。 |
| 外部依赖多 | LLM、Embedding、Judge、数据库、Redis 都可能影响演示 | 准备健康检查、演示数据和录屏备份。 |
| 前端页面交互复杂 | 学生端、管理端、AI 面板和课堂页面状态多 | 通过组件化、路由分层和契约测试降低回归。 |

## 6. 实训收获

### 6.1 技术收获

1. 熟悉了 Spring Boot 后端开发，包括 Controller、Service、Validation、Security、Redis Session、Flyway 和 Actuator。
2. 熟悉了 Vue 3 前端开发，包括路由、状态管理、组件拆分、代码编辑器和管理端页面。
3. 理解了 PostgreSQL、Redis、pgvector、Memgraph、NATS 和 Temporal 在复杂系统中的作用。
4. 学习了 AI Tutor、RAG、Prompt、安全过滤、学习者画像和 AI 可观测性的工程实现。
5. 加深了对自动化测试、契约测试、E2E 测试和部署验证的理解。

### 6.2 工程收获

1. 复杂项目必须先明确边界，再写代码。
2. 文档不能只写“理想设计”，必须能对应真实代码和运行环境。
3. 数据库迁移、环境变量和外部服务配置是工程交付中非常关键的部分。
4. AI 功能不只是调用模型，还需要上下文、检索、权限、安全和质量评估。
5. 可观测性不是上线后再补的功能，而是调试复杂系统的基础设施。

### 6.3 团队与表达收获

通过整理技术文档和答辩材料，我更加理解如何向不同对象表达项目：对教师要说明课程价值和完成度，对开发者要说明架构和实现，对用户要说明功能和使用流程。一个好的项目不仅要能运行，还要能被讲清楚、被验证、被维护。

## 7. 不足与改进

1. 需要在最终提交前补充真实运行截图和测试执行结果。
2. 需要根据学院提供的模板调整实训总结报告格式。
3. 需要录制正式演示视频，避免答辩当天依赖临时环境。
4. 需要进一步压缩答辩重点，避免因为功能太多导致讲解分散。
5. 需要持续清理历史文档中已下线模块的残留描述。

## 8. 自我评价

本次实训完成了一个功能复杂、技术栈较完整、具有真实教育场景价值的软件系统。通过项目开发，我不仅练习了前后端和数据库开发，也接触了 AI 工程、RAG、可观测性、部署和测试等更接近真实工程的软件开发内容。虽然项目仍有外部服务依赖、演示环境稳定性和文档模板适配等问题，但整体已经具备课程提交和答辩展示的基础。
