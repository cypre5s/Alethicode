# Alethicode 项目计划

> 文档编号：ALETHICODE-PLAN-COURSE-2026  
> 版本：v1.0  
> 状态：课程提交版  
> 参考标准：ISO/IEC/IEEE 12207、PMBOK 软件项目管理实践  
> 适用范围：Alethicode 智能在线评测与 AI 导学平台的课程设计、开发、测试、部署和答辩交付。

## 1. 项目概述

### 1.1 项目背景

传统在线评测系统通常只给出 Accepted、Wrong Answer、Runtime Error 等判题结果，对非计算机专业初学者来说反馈过于简短，难以回答“为什么错”“该如何修改”“下一步练什么”这些学习问题。与此同时，通用 AI 问答工具虽然能解释代码，但缺少课堂上下文、真实判题结果、课程课件和学生历史学习画像，容易出现脱离课程目标、给出过度答案或直接泄题的问题。

Alethicode 的项目目标是在真实 OJ 判题闭环上叠加 AI 导学、课件 RAG、课堂协作和学习者画像能力，形成一个面向 Python 初学者、教师可管理、系统可观测的智能编程教育平台。

### 1.2 项目目标

1. 建设可运行的在线评测平台，支持用户注册登录、题库浏览、代码提交、判题反馈和提交历史查询。
2. 建设 AI Tutor 导学能力，围绕读题、构思、脚手架、编码、错误反馈、AC 复盘和迁移练习形成阶段化辅导。
3. 建设课件问答和语言包能力，使 AI 回答能够基于教师上传课件、知识点和课程页面引用。
4. 建设教师课堂协作能力，支持班级、课堂、作业、监控、AI 出题和学情分析。
5. 建设后台管理能力，支持题库、测试用例、语言包、账号、系统配置、AI 可观测性和使用统计。
6. 建设工程化质量保障体系，包括数据库迁移、自动化测试、接口契约、可观测性、部署脚本和安全控制。

### 1.3 项目成功标准

| 类别 | 成功标准 |
|---|---|
| 功能完整性 | 学生端、教师端、管理端、AI Tutor、课件问答和核心判题流程可以形成端到端闭环。 |
| 教学适配 | 面向 Python 初学者，AI 反馈遵循启发式、阶段化和不直接给出完整答案的教学策略。 |
| 工程质量 | 代码结构清晰，关键模块有自动化测试或契约测试，数据库变更通过 Flyway 管理。 |
| 可部署性 | 支持本地开发和 Docker Compose 部署，核心依赖包括 PostgreSQL、Redis、Judge Server、RAG 和 Tutor Graph 服务。 |
| 可答辩性 | 能通过 PPT、演示视频和技术文档清晰说明项目背景、设计、实现、测试和创新点。 |

## 2. 项目范围

### 2.1 范围内功能

| 模块 | 范围 |
|---|---|
| 账号与权限 | 注册、登录、退出、个人资料、密码重置、管理员/教师/学生角色区分、会话管理。 |
| 题库与评测 | 题目列表、题目详情、代码编辑器、提交判题、提交详情、测试用例管理、Judge Server 集群管理。 |
| AI Tutor | 阶段化导学、上下文引用、学习者画像、EvidencePack、Reflection、自适应提示、对话压缩、分叉、WebSocket 恢复。 |
| 语言包与课件 | 语言包初始化、课件页面解析、知识点抽取、课件问答、引用解析、视频生成任务、质量报告。 |
| 课堂协作 | 班级、成员、课堂、作业、教师监控、AI 智能组卷和课堂分析。 |
| 学习复盘 | 学习者笔记本、错题复习包、知识点掌握度、练习热力图和推荐。 |
| 后台管理 | 用户、题目、公告、系统配置、AI 配置、可观测性、Beta 反馈、使用统计。 |
| 基础设施 | PostgreSQL、Redis、pgvector、Memgraph、NATS、Temporal、Docker Compose、Prometheus、Jaeger、Sentry/GlitchTip。 |

### 2.2 范围外功能

1. 当前 README 标注 Career 模块已下线，因此课程演示不把 Career 作为核心功能。
2. 不承诺覆盖所有编程语言的深度教学，课程定位优先保障 Python 初学者体验。
3. 不把外部 LLM、Embedding、TTS、Judge Server 作为本项目自研范围，它们作为外部依赖或可替换服务接入。
4. 不在课程提交文档中承诺商业级 SLA，但会说明可靠性、可观测性和部署约束。

## 3. 项目组织

### 3.1 角色分工

| 角色 | 主要职责 |
|---|---|
| 项目负责人 | 明确目标范围、里程碑、风险和答辩交付。 |
| 后端开发 | Spring Boot 服务、数据库迁移、权限、安全、AI 网关、业务服务和接口测试。 |
| 前端开发 | Vue 页面、路由、状态管理、代码编辑器、AI 交互组件、响应式布局和前端测试。 |
| AI/算法开发 | Prompt 设计、RAG 检索、Tutor 工作流、学习者画像、LLM 评估和安全过滤。 |
| 测试负责人 | 测试计划、测试用例、回归测试、缺陷记录和质量结论。 |
| 运维负责人 | Docker Compose、环境变量、监控、日志、部署和演示环境维护。 |
| 文档负责人 | 技术文档、PPT、实训总结、演示脚本和验收材料。 |

### 3.2 沟通机制

1. 每个阶段结束后输出阶段性说明，包括已完成事项、未完成事项、风险和下一步计划。
2. 需求变更必须说明影响范围，特别是数据库、接口、权限、前端路由和演示路径。
3. 与外部服务相关的风险必须提前记录，包括 LLM Key、Embedding Key、Judge Token、数据库连接和 Redis 密码。

## 5. 里程碑计划

| 阶段 | 里程碑 | 目标产物 | 验收方式 |
|---|---|---|---|
| M1 | 基础 OJ 闭环 | 登录、题库、题目详情、提交判题、提交列表 | 手工提交样例题并查看判题结果。 |
| M2 | 后台管理 | 题目、测试用例、公告、用户、判题服务器管理 | 管理端创建题目并在学生端提交。 |
| M3 | AI Tutor 初版 | AI 导学入口、任务状态、错误解释、AC 复盘 | 针对一道 Python 题演示阶段化辅导。 |
| M4 | 课件与语言包 | 课件上传/解析、语言包初始化、知识点、课件问答 | 上传课件后基于页面引用问答。 |
| M5 | 课堂协作 | 班级、成员、课堂、作业、监控、AI 出题 | 教师创建班级和作业，学生加入并提交。 |
| M6 | 学习者画像 | 掌握度、错题复习、学习记忆、推荐练习 | 学生多次提交后查看画像和复习入口。 |
| M7 | 可观测性和稳定性 | 指标、日志、追踪、限流、熔断、缓存 | 通过管理端或监控端查看 AI/系统状态。 |
| M8 | 课程交付 | 文档、PPT、演示脚本/视频、源代码 | 按课程要求提交并答辩演示。 |

## 6. 进度管理

### 6.1 计划基线

| 工作项 | 预计工期 | 前置依赖 | 输出 |
|---|---:|---|---|
| 需求分析 | 3-5 天 | 项目选题 | 需求规格说明书 |
| 架构设计 | 3-5 天 | 需求确认 | 概要设计说明书 |
| 数据库与接口设计 | 4-7 天 | 架构确认 | ER、迁移、接口草案 |
| OJ 主流程开发 | 7-14 天 | 数据库和接口 | 前后端主流程 |
| AI Tutor 开发 | 10-20 天 | OJ 主流程 | AI 导学能力 |
| 语言包/RAG 开发 | 10-20 天 | 课件模型和外部依赖 | 课件问答能力 |
| 课堂与管理端 | 7-14 天 | 用户和题库 | 教师与管理员功能 |
| 测试与部署 | 5-10 天 | 主功能完成 | 测试报告、部署环境 |
| 文档与答辩 | 3-7 天 | 功能稳定 | 提交材料 |

### 6.2 进度控制方法

1. 使用里程碑验收，而不是只按代码提交数量判断进度。
2. 每个里程碑保留可演示路径，确保答辩时不依赖未完成分支。
3. 将外部服务相关功能设置为高风险项，提前准备演示账号、环境变量和降级说明。
4. 数据库变更必须先写迁移，再写代码，避免环境漂移。

## 7. 质量管理计划

| 质量目标 | 控制措施 |
|---|---|
| 需求可追踪 | 每个核心功能在需求文档、设计文档和测试文档中保持编号对应。 |
| 代码可维护 | 后端按 Controller-Service-Repository/Client-DTO 分层，前端按页面、组件、API、状态和工具拆分。 |
| 数据可迁移 | 使用 Flyway 管理数据库 schema，避免手工改库。 |
| 接口可验证 | 后端存在控制器契约测试和集成测试，前端存在契约测试和 E2E 测试。 |
| 安全可控 | Spring Security、Session Redis、CSRF、内部 API Key、输入校验、审计日志和敏感日志控制。 |
| 运行可观测 | Actuator、Prometheus、Micrometer、OpenTelemetry、Jaeger、Sentry/GlitchTip 和业务追踪。 |
| 教学可信 | AI 回答基于题目、提交、课件和学习者上下文，配合安全过滤和 Reflection 自检。 |

## 8. 风险管理计划

| 风险编号 | 风险 | 概率 | 影响 | 应对措施 |
|---|---|---|---|---|
| R-01 | 外部 LLM/Embedding 服务不可用 | 中 | 高 | 配置多模型网关、熔断、重试、缓存和演示前健康检查。 |
| R-02 | Judge Server 环境不稳定 | 中 | 高 | 独立健康检查、Token 管理、判题服务器监控和最小题目演示集。 |
| R-03 | 文档与代码事实不一致 | 高 | 中 | 以构建配置、路由、控制器、迁移和测试目录为基线重新核验。 |
| R-04 | 功能范围过大导致答辩重点分散 | 中 | 中 | 答辩聚焦 OJ 主流程、AI Tutor、课件 RAG、课堂协作和工程质量。 |
| R-05 | 数据库迁移影响历史数据 | 中 | 高 | 使用 Flyway、增量迁移、上线前备份和回滚预案。 |
| R-06 | AI 回答存在幻觉或泄题 | 中 | 高 | EvidencePack、课件引用、Prompt Safety Filter、Reflection 和拒答边界。 |
| R-07 | 演示视频录制时环境异常 | 中 | 中 | 提前录制、准备脚本、准备本地截图和接口健康检查。 |

## 9. 配置管理计划

1. 源代码以 Git 仓库为唯一版本源。
2. 数据库结构以 `backend/src/main/resources/db/migration` 下 Flyway 文件为准。
3. 环境变量来自 `backend/.env.example`、`deploy/.env.example` 和 Docker Compose 配置。
4. 文档新增在 `docs/course-submission/`，不覆盖已有项目文档。
5. 课程提交版文档按版本号和日期管理，后续修改需要记录改动范围。

## 10. 验收计划

| 验收项 | 验收准则 |
|---|---|
| 源代码 | 仓库结构完整，后端、前端、微服务、部署脚本和文档目录齐全。 |
| 技术文档 | 项目计划、需求规格、概要设计、详细设计、测试计划和报告、项目总结齐全。 |
| 实训总结 | 有任务说明、过程记录、问题分析、学习收获和反思。 |
| 答辩 PPT | 能在 8-12 分钟内讲清背景、架构、核心功能、测试、创新和总结。 |
| 演示视频 | 展示登录、题目、提交、AI Tutor、课件问答、课堂/管理端等核心链路。 |
| 演示环境 | 前端、后端、数据库、Redis、Judge Server、RAG/Tutor Graph 关键服务可用。 |

## 11. 项目收尾

项目收尾阶段需要完成以下动作：

1. 归档课程提交材料。
2. 检查所有文档中的版本、日期、术语和项目名称一致。
3. 根据实际演示环境更新截图、视频和测试结论。
4. 删除文档中的临时占位符。
5. 准备答辩常见问题，包括技术选型、AI 安全、性能、数据一致性、测试覆盖和后续规划。
